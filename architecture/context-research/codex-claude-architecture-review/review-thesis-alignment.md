## Review

- Correct: The main thesis and synthesis docs are broadly aligned on the library-first enforcement substrate. `docs/thesis.md:21-31` says Provenant is a Go library with optional MCP/CLI/runtime shells over the same kernel, and `architecture/OVERVIEW.md:9-45` repeats the same boundary: pure kernel, thin access surfaces, storage outside the kernel, byte-identical deterministic audit chains across surfaces.
- Correct: Mode B non-bypassability is appropriately scoped rather than overclaimed. `docs/thesis.md:17` explicitly says MCP/host-channel text can bypass `submit_answer` and is not Provenant-signed; `architecture/subsystems/harness.md:84-89` and `architecture/adapters/mcp.md:84-89` repeat that limitation and recommend Mode A for full enforcement.
- Correct: The “cleaning is provenanced too” thesis has concrete architecture support. `architecture/OVERVIEW.md:150-157`, `architecture/tools/README.md:21-32`, and `architecture/subsystems/skills.md:156-213` define match/dedupe plus audit-visible built-in normalizers.
- Correct: Storage-as-deployment-concern is now well supported in the synthesis docs. `architecture/OVERVIEW.md:53-56` and `architecture/OVERVIEW.md:234-237` state no kernel database requirement, optional runtime persistence, and stateless/in-memory operation where HITL persistence is not needed.

- Blocker: Stale MCP-primary and Postgres/S3-required language still contradicts the library-first / equal-adapter thesis in the MCP adapter doc. `architecture/adapters/mcp.md:3-16` labels MCP “primary,” points readers to superseded ADR-0007, and frames “MCP first”; `architecture/adapters/mcp.md:127-132` shows only Postgres/S3 config; `architecture/adapters/mcp.md:143-157` says local dev is “postgres + minio” and “State lives in Postgres and S3.” This conflicts with `architecture/OVERVIEW.md:43-45`, `architecture/OVERVIEW.md:57`, `architecture/OVERVIEW.md:237`, and ADR-0010. Recommendation: revise `architecture/adapters/mcp.md` to “v0 / equal first-class adapter,” cite ADR-0010, show SQLite-by-default and stateless/memio configs, and make Postgres/S3 explicitly optional multi-process or large-payload runtime bindings.

- Blocker: Normalizer determinism has internal contradictions that undercut replay-deterministic claims for the messy-data part of the thesis. `architecture/subsystems/skills.md:196` says `date.iso8601_lenient.tz_defaulted` is in the deterministic sub-object; `plans/implementation-plan.md:97` says the same fixture should assert `tz_defaulted = true` in the non-deterministic sub-object. The same skills doc also says the v0 registry is non-empty at `architecture/subsystems/skills.md:207`, but then says “Phase 2 task list does not load any normalizer (the registry is empty)” at `architecture/subsystems/skills.md:209`; the plan agrees with the non-empty registry at `plans/implementation-plan.md:85`. Recommendation: make `tz_defaulted` deterministic everywhere, remove the stale “registry is empty” sentence, and ensure ADR-0006’s cycle-6 empty-registry text is visibly superseded by cycle 9 in downstream references.

- Note: The architecture README still has stale/incomplete navigation that can mislead thesis reviewers. It lists ADR-0007 as “MCP as the primary adapter” without marking it superseded at `architecture/README.md:127`, while ADR-0010 is the active decision at `architecture/README.md:130`; its tool category table omits `match` and `dedupe` at `architecture/README.md:106-113`, while the v0 scope summary includes them at `architecture/README.md:161`. Recommendation: mark ADR-0007 superseded in the table and add match/dedupe rows to the tool table.

- Note: Some subsystem docs still imply storage persistence as a subsystem dependency rather than a deployment/runtime concern. `architecture/subsystems/skills.md:7-10` says pack manifests and versions persist via `subsystems/storage.md`, and `architecture/subsystems/harness.md:279-300` presents a concrete SQL `runs` table immediately after Mode A/Mode B harness behavior. This is not necessarily architecturally wrong for runtime bindings, but it reads as required storage unless qualified. Recommendation: annotate these sections as “runtime/reference persistence only”; for library mode, state that pack metadata/run state are in-memory values or host-owned bytes.

- Note: The strongest thesis claims about tamper-evidence and byte-identity are acceptable only with the documented caveats. `docs/KNOWN_TRADE_OFFS.md` scopes tamper-evidence to an internal hash chain without external notary, host conformance to self-declaration in v0, and fresh-run byte identity to captured deterministic replay rather than independently changing upstream sources. Recommendation: in any report, phrase claims as “internally tamper-evident audit pack,” “Provenant-signed answers only after submit_answer,” and “byte-identical deterministic portions for the same captured inputs / pinned deployment facts,” not as external notarization or arbitrary cross-deployment equivalence.
