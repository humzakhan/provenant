## Review

- Correct: The current architecture largely aligns the sweeper/persistence model with the library-first thesis where it is explicit. `architecture/OVERVIEW.md:39-45` and `architecture/subsystems/storage.md:1-28` state that the kernel has no storage requirement, ships only `kernel/public/memio/`, and leaves persistence to hosts or optional runtime bindings. `architecture/subsystems/storage.md:54-71` correctly scopes library-mode HITL pause/resume to host-serialized `RunState`, and `architecture/subsystems/kernel.md:372-416` defines a canonical, byte-stable `RunState` snapshot rather than kernel-owned persistence.
- Correct: The orphan threshold itself is designed for cross-mode deterministic bytes. The skill-pinned `bounds.orphan_multiplier` is not deployment-overridable (`architecture/subsystems/skills.md`, manifest section) and the sweep records `threshold_seconds_used` in the deterministic payload (`architecture/subsystems/harness.md:222-224`, `architecture/subsystems/audit.md:159`). This avoids a common SaaS/runtime leak where each deployment chooses its own orphan timeout and diverges audit bytes.
- Correct: The atomicity boundary is appropriately abstracted as a kernel-public interface instead of Postgres policy. `TransactionalScope` rejects split substrates at boot/runtime (`architecture/subsystems/kernel.md:284-358`), and the parallel-buffer flush rule writes tokens and audit entries in one transaction (`architecture/subsystems/audit.md:270-283`). The in-memory binding is explicitly treated as a first-class substrate, not a fake DB (`architecture/subsystems/storage.md:26-28`).

- Blocker: Kernel subsystem text still smuggles the old database-centric model into the kernel. `architecture/subsystems/kernel.md:7-9` says the kernel depends on `storage.md` / “Postgres + object store”, `architecture/subsystems/kernel.md:19-20` says a kernel responsibility is to “Persist tokens,” and later token-store prose still frames Postgres as source-of-truth. This conflicts directly with ADR-0011 and `architecture/subsystems/storage.md:1-28`. Recommendation: rewrite the kernel responsibility/dependency sections to say the kernel mints/verifies tokens against injected `Store`/`AuditSink` interfaces and that persistence is optional host/runtime projection. Reserve Postgres schema language for `storage.md` only.

- Blocker: The orphan sweeper is not consistently scoped to runtime/host persistence. `architecture/subsystems/harness.md:199-224` describes “Orphan-run sweep at startup” and lookup from a `skills` table as if every mode has a daemon startup and a database. That is true for SQLite/Postgres runtime bindings, but not for default library mode, where process death loses in-memory state unless the host has serialized its own state (`architecture/subsystems/storage.md:54-71`). Recommendation: split this into two explicit contracts: (1) `kernel.OrphanCandidates` / recovery-finalization pure functions over a host-provided run snapshot + skill registry; (2) runtime startup sweeper implemented by SQLite/Postgres bindings. Replace “skills table” in `harness.md:224` with “skill registry / persisted skill metadata supplied by the host or runtime binding,” with the table as only one projection.

- Note: The implementation plan contains an internal phase contradiction that can reintroduce runtime persistence assumptions too early. Phase 1 correctly limits orphan work to in-memory detection units and defers cross-process recovery to Phase 4 (`plans/implementation-plan.md:46-68`). But Phase 3 still says the CLI run has “Full audit + tokens + guard outcomes persisted” and includes a `provenant-server` kill/restart orphan test in Phase 3 (`plans/implementation-plan.md:106-127`), while runtime server/persistent bindings are deferred to Phase 4 (`plans/implementation-plan.md:131-150`). Recommendation: remove the Phase 3 orphan-recovery done-when item (or mark it superseded) and keep the authoritative end-to-end sweep test only in Phase 4 against SQLite and Postgres.

- Note: `run_orphan_recovered.recovery_reason` is deterministic but not pinned as an enum (`architecture/subsystems/audit.md:159`). Independent bindings could emit `startup_sweep`, `startup`, or `orphan_sweep` for the same recovery. Recommendation: add a small canonical enum for `recovery_reason` (e.g., `startup_sweep`, `operator_sweep`, `restore_verify_prepass`) and generate/validate it like `failure_subcode`.

- Note: The sweeper model should explicitly state that default library-mode in-memory runs have no cross-process orphan recovery. That is implied by `architecture/subsystems/storage.md:26-28` and `:54-71`, but the generic termination table in `harness.md:185-224` reads as universal. Recommendation: add a short “Mode scope” paragraph near the orphan threshold section: in-memory library mode can detect/finalize stale runs only while the host retains the in-memory snapshot; after process death, recovery requires host-persisted `RunState`/run snapshot or a runtime binding. This keeps the thesis honest: no hidden SaaS/database promise in the kernel.
